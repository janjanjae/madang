## 실행·테스트 명령
<!-- 과제별: 설치 / 실행 / 테스트 / 빌드 명령 -->
- 서버는 `0.0.0.0`에 바인딩하고 포트를 명시한다 (예: `--host 0.0.0.0 --port 8000`). 사용 포트는 여기 적는다.
- 서버·watch처럼 계속 도는 프로세스는 별도 터미널에서 실행한다. 작업 터미널을 막지 않는다.
- 안 쓰는 서버·프로세스는 끈다 (메모리 초과 방지).

## 작업 방식
1. 질문 → 기획서 → 코드 순서를 지킨다. 판단이 필요한 것을 먼저 묻고(최대 2라운드·10분), `plan.md`를 쓰고(문제 정의, 필수/선택 범위, 가정, 구현 결정, 검증 방법), 사람이 승인한 뒤 기능을 구현한다. 단 답과 무관한 준비 작업(데이터 로딩·서버 뼈대·mock 화면)은 팀장 판단으로 질문 라운드와 동시에 해도 된다. (`$planning-and-task-breakdown`)
2. 얇은 수직 슬라이스로 만든다. 첫 슬라이스는 화면→API→더미 로직→화면 끝까지 연결(한 서버 서빙). 슬라이스마다 실행·확인 후 커밋. (`$incremental-implementation`)
3. 코드를 쓰기 전에 사다리를 돈다 — 꼭 필요한가 → 이미 있나 → 표준·플랫폼 → 설치된 의존성 → 한 줄 → 최소 구현. 단 문제를 이해한 다음에.
4. 요청받지 않은 기능·추상화·의존성을 추가하지 않는다. 범위 밖 발견은 기록만.
5. 에러가 나면 기능 추가를 멈추고 재현 → 원인 → 수정 → 회귀 테스트. (`$debugging-and-error-recovery`)

## 완료 주장
- 검증 명령을 실제로 실행하고 출력을 확인하기 전에는 "완료·통과·수정됨"을 말하지 않는다. (`$verification-before-completion`)
- 슬라이스를 끝낼 때 건너뛴 것·확인 못 한 것·위험을 한두 줄로 남긴다.

## 커밋
- 작은 단위, 한 커밋 = 한 논리적 변경. 메시지에 "왜"를 담는다.
- 비밀키·토큰·`.env`는 커밋하지 않는다. 키를 코드에 하드코딩하지 않는다.

## 기록
- 판단이 들어간 결정은 `plan.md` 하단 "결정 로그"에 한 줄: `HH:MM 결정 — 왜(사람의 말 그대로) / 버린 대안 / 확인 방법`.
- 기록 트리거: 알고리즘·방식 선택 · 규칙을 필수/선택(하드/소프트)으로 가름 · 가정 채택 · 범위 버림 · 버그 원인.
- 알려진 한계가 있는 지름길은 `shortcut: <한계>, <언제 업그레이드>` 주석.

## 스킬 호출 규칙
- 계획을 세울 때 → `$planning-and-task-breakdown`
- 여러 파일에 걸친 구현 → `$incremental-implementation`
- 같은 에러에 두 번 실패하면 → `$debugging-and-error-recovery` (그래도 안 되면 solver 에이전트)
- "완료·통과·수정됨"이라고 말하기 직전 → `$verification-before-completion`
- 팀으로 나눌 때 → `$teamleader` (팀장 탭에서만)
- 제출 직전, 사람이 부를 때 → `$defense-drill` (이해 질문 + 모범 답안, 코드 수정 없음)
- 팀장 탭 컨텍스트가 절반을 넘었거나 단계가 바뀔 때, 사람이 부를 때 → `$checkpoint`

## 팀 (마당)
- 기본은 팀장 탭(`$teamleader`)에서 plan.md를 쓰고 팀원 탭으로 나누는 탭 모드. 아주 작은 과제만 탭 하나(단일 모드).
- 문서 역할: `plan.md` = 큰 계획·결정 로그(왜)·검증 결과·남은 한계 · `.team/TASKS.md` = 배정판(ID·담당·영역·상태) · `.team/PROGRESS.md` = 진행 로그(언제 무슨 일, 추가만). 같은 내용을 두 곳에 쓰지 않는다. 제출 문서 이름·틀은 과제 안내가 1순위.
- 팀원: 번뜩(solver, 깊이) · 몽글(builder, 넓이) · 슥슥(sketcher, 시안) · 조잘(narrator, 해설·읽기 전용) — `.codex/agents/*.toml`
- 신호 파일: `.team/briefs/<인스턴스>.md` → `.team/confirm/<인스턴스>.request.md` → `reply.md`(APPROVE/FIX). 대기는 사람이 탭을 돌며 깨운다.
- 허브 문서 `.team/TASKS.md`·`.team/PROGRESS.md`는 팀장만 고친다.

## 효율
- 같은 요청을 반복하지 않는다. 두 번 실패하면 멈추고 가설을 다시 세운다.
- 필요한 파일만 읽는다. 큰 출력은 요약해서 본다.
- sleep·폴링 루프로 기다리지 않는다(백그라운드 확인 반복이 토큰을 태운다).
