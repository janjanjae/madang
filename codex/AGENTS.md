## 실행·테스트 명령
<!-- 과제별: 설치 / 실행 / 테스트 / 빌드 명령 -->
- 서버는 `0.0.0.0`에 바인딩하고 포트를 명시한다 (예: `--host 0.0.0.0 --port 8000`). 사용 포트는 여기 적는다.
- 서버·watch처럼 계속 도는 프로세스는 별도 터미널에서 실행한다. 작업 터미널을 막지 않는다.
- 안 쓰는 서버·프로세스는 끈다 (메모리 초과 방지).

## 작업 방식
1. 구현 전에 `plan.md`를 쓴다: 문제 정의, 필수/선택 범위, 가정, 검증 방법. (`$planning-and-task-breakdown`)
2. 얇은 수직 슬라이스로 만든다. 슬라이스마다 실행·확인 후 커밋. (`$incremental-implementation`)
3. 코드를 쓰기 전에 사다리를 돈다 — 꼭 필요한가 → 이미 있나 → 표준·플랫폼 → 설치된 의존성 → 한 줄 → 최소 구현. 단 문제를 이해한 다음에.
4. 요청받지 않은 기능·추상화·의존성을 추가하지 않는다. 범위 밖 발견은 기록만.
5. 에러가 나면 기능 추가를 멈추고 재현 → 원인 → 수정 → 회귀 테스트. (`$debugging-and-error-recovery`)

## 완료 주장
- 검증 명령을 실제로 실행하고 출력을 확인하기 전에는 "완료·통과·수정됨"을 말하지 않는다. (`$verification-before-completion`)
- 슬라이스를 끝낼 때 건너뛴 것·확인 못 한 것·위험을 한두 줄로 남긴다.

## 커밋
- 작은 단위, 한 커밋 = 한 논리적 변경. 메시지에 "왜"를 담는다.
- 비밀키·토큰·`.env`는 커밋하지 않는다. 키를 코드에 하드코딩하지 않는다.

## 기록
- 방향을 바꾼 결정은 `plan.md` 하단 "결정 로그"에 시각과 이유 한 줄.
- 알려진 한계가 있는 지름길은 `shortcut: <한계>, <언제 업그레이드>` 주석.

## 효율
- 같은 요청을 반복하지 않는다. 두 번 실패하면 멈추고 가설을 다시 세운다.
- 필요한 파일만 읽는다. 큰 출력은 요약해서 본다.
