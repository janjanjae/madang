# Incremental Implementation

## Overview

얇은 수직 슬라이스로 만든다 — 한 조각 구현 → 테스트 → 확인 → 커밋 → 다음 조각.
기능 전체를 한 번에 짜지 않는다. 각 조각이 끝날 때마다 시스템은 동작·테스트 가능한 상태여야 한다.

## When to Use

- 여러 파일에 걸친 변경
- 태스크 목록(plan.md)에서 기능을 구현할 때
- 기존 코드 리팩터링
- 테스트 없이 ~100줄 넘게 쓰고 싶어질 때

**When NOT to use:** 범위가 이미 최소인 단일 파일·단일 함수 변경 (단, Rule 0 사다리는 그때도 적용).

## The Increment Cycle

```
구현 ──→ 테스트 ──→ 확인 ──→ 커밋 ──→ 다음 슬라이스
```

1. **구현** — 가장 작은 완결 기능 조각
2. **테스트** — 테스트 실행
3. **확인** — 실제로 동작하는지(테스트 통과, 빌드 성공, 화면·API 직접 확인)
4. **커밋** — 의도가 드러나는 메시지
5. **다음 슬라이스**

## Slicing Strategy (Vertical)

각 슬라이스는 스택 전체를 관통하는 완전한 경로:

```
Slice 1: 데이터 모델 + 저장 로직        → 테스트 통과, API로 생성·조회 확인
Slice 2: 목록 API + 필터               → 테스트 통과, curl로 응답 확인
Slice 3: 화면 표시 + API 연결           → 브라우저에서 목록·필터 동작 확인
```

## Implementation Rules

### Rule 0: 가장 작은 완결 변경 (Simplicity First)

**쓰기 전에 — 이해가 먼저.** 태스크와 그게 건드리는 코드를 읽고, 변경이 닿아야 하는 곳을 전부 적는다:
호출부·테스트·픽스처·설정·export. 그리고 이 변경이 사용자에게 무엇을 깨뜨릴 수 있는지(데이터 파괴·노출, 동작이 멈추는 호출부) 확인한다.
그게 범위다. 추가 기능은 범위가 아니다.

**사다리 — 위에서부터, 완전히 동작하는 첫 칸에서 멈춘다:**
1. **꼭 있어야 하나?** 아무도 요청하지 않은 기능·옵션·유연성은 건너뛰고 한 줄로 이름만 남긴다. 모호한 요청("X 만들어줘")은 핵심만 하는 가장 작은 버전으로.
2. **이미 코드베이스에 있나** (헬퍼·컴포넌트·서비스·패턴)? → 주변 코드가 쓰는 방식 그대로 재사용
3. **표준 라이브러리·플랫폼 기능으로 되나?** → 사용. 단 프로젝트 자체 컴포넌트가 있으면 그게 네이티브 위젯보다 우선
4. **이미 설치된 의존성으로 되나?** → 사용. 몇 줄 때문에 의존성을 추가하지 않는다
5. **한눈에 읽히는 한 줄로 되나?** → 한 줄로
6. 그래도 없을 때만 최소 구현

**사다리는 반사신경이지 리서치 프로젝트가 아니다 — 단, 문제를 이해한 *다음에* 돈다.**
엉뚱한 자리의 가장 작은 변경은 게으른 게 아니라 두 번째 버그다. 최단 diff는 닿아야 할 곳을 다 알고 났을 때만 정답이다. 해독이 필요한 한 줄은 짧은 게 아니다.

**해법은 게으르게, 변경은 끝까지:**
- 태스크에 필요한 부분은 전부 끝낸다 — 내 변경이 깨뜨리는 호출부·테스트·픽스처 포함.
- 요청 없는 추상화·래퍼·타입 변환·옵션·설정·보일러플레이트·"나중을 위한" 코드 금지. 삭제가 추가를 이긴다. 코드베이스의 기존 구조(레이어·인터페이스·컨벤션)를 유지.
- 버그 수정: 고치기 전에 그 함수의 호출부를 전부 grep → 공유 코드에서 근본 원인을 한 번 고친다.
- 옮기거나 합친 코드는 원래의 에러 처리·검증을 유지한다.
- 크기가 같은 선택지면 엣지 케이스에서 맞는 쪽.
- **검증 없는 게으른 코드는 미완성이다**: 새 비자명 로직(분기·루프·파서·돈·보안, 새 스크립트·앱)은 작은 테스트나 assert 셀프체크 하나를 남긴다. 자명한 변경은 불필요.
- 알려진 한계가 있는 지름길은 주석으로: `shortcut: <한계>, <언제 업그레이드>`
- 주석은 코드가 보여줄 수 없는 "왜"만, 한 줄.

**절대 깎지 않는 것:** 신뢰 경계의 입력 검증, 데이터 손실을 막는 에러 처리, 보안, 접근성, 요청받은 것 전부.

**네이티브 우선 예시:**
```
✗ 날짜 선택에 피커 라이브러리 추가      ✓ <input type="date">
✗ 검증 로직을 앱 코드로 중복 구현        ✓ DB 제약(NOT NULL, UNIQUE, CHECK)
✗ 단순 토글에 상태관리 라이브러리        ✓ CSS / 네이티브 기능
✗ 알림 하나를 위한 이벤트버스 파이프라인  ✓ 단순 함수 호출
```
비슷한 코드 3줄이 성급한 추상화보다 낫다.

### Rule 0.5: Scope Discipline

태스크가 요구하는 것만 건드린다. 옆 코드 "정리", 안 고치는 파일의 import 정리, 이해 못 한 주석 삭제, 스펙에 없는 "유용해 보이는" 기능 — 하지 않는다.
범위 밖에서 발견한 것은 고치지 말고 기록만:
```
NOTICED BUT NOT TOUCHING:
- utils.ts에 사용하지 않는 import (이 태스크와 무관)
```

### Rule 1: 한 번에 하나 — 각 커밋은 하나의 논리적 변경
### Rule 2: 항상 빌드 가능 — 각 슬라이스 후 빌드·기존 테스트 통과
### Rule 3: 되돌리기 쉽게 — 각 슬라이스는 독립적으로 revert 가능. DB 마이그레이션은 rollback 포함

## Increment Checklist

각 슬라이스 후 (plan.md의 해당 태스크 체크박스도 갱신):

- [ ] 변경이 한 가지를 완전히 함
- [ ] 기존 테스트 통과 (프로젝트의 테스트 명령 — AGENTS.md 참조)
- [ ] 빌드·타입 체크·린트 통과 (있다면)
- [ ] 새 기능이 예상대로 동작 (직접 실행해 확인)
- [ ] 의도가 드러나는 메시지로 커밋

## 응답 마무리

슬라이스를 끝낼 때 한두 줄: **건너뛴 것·확인 못 한 것**, 그리고 사용자가 알아야 할 위험.

## Red Flags

- 테스트 없이 100줄 이상 작성
- 한 슬라이스에 무관한 변경 여러 개
- "이것도 빠르게 추가하자" 범위 확장
- 테스트·확인 단계 건너뜀
- 슬라이스 사이에 빌드·테스트 실패
- 커밋 안 된 대량 변경 누적
- 세 번째 사용 사례 전에 추상화
