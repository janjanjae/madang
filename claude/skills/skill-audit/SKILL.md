# skill-audit

스킬·커맨드·에이전트 인벤토리를 실제 파일 기준으로 전수 스캔하고, `~/.claude/REGISTRY.md`(개인 환경 원장)를 현행화한다.
**SSOT는 파일 시스템** — 레지스트리는 손으로 관리하는 목록이 아니라 스캔 결과에서 파생되는 문서다.

## 언제 사용하나

- 성찰 루틴의 일부로 **월 1회 또는 스프린트 종료 시** (팀장 세션에서)
- 스킬/커맨드를 새로 만들거나 폐기·이동했을 때 즉시
- "이 스킬 뭐더라" 같은 질문이 반복될 때 (레지스트리가 썩었다는 신호)

## 실행 절차

### 1. 전수 스캔

아래 위치를 스캔한다. **심링크 여부로 관리 주체를 구분**한다 (심링크 → madang 레포(구 pokemon-agent-team) 관리분, 실디렉토리/실파일 → 로컬 전용).

```bash
# 범용 (개인 글로벌)
ls -la ~/.claude/skills/ ~/.claude/commands/ ~/.claude/agents/

# 프로젝트 오버레이 (현재 프로젝트에서 실행 중일 때)
ls {프로젝트 루트}/.claude/skills/ {프로젝트 루트}/.claude/commands/ {프로젝트 루트}/.claude/agents/ 2>/dev/null
```

### 2. REGISTRY.md 대조 → 차이 감지

`~/.claude/REGISTRY.md`와 스캔 결과를 비교해 보고한다:

- **신규**: 파일은 있는데 레지스트리에 없음 → 분류(축 2개) 판정 후 등재
- **유령**: 레지스트리에 있는데 파일이 없음 → 삭제 또는 폐기 표기
- **이동**: 스코프가 바뀐 것 (예: 프로젝트 → 범용 승격, 레포 공유 → 개인 이관)

### 3. 항목별 판정 (skill-guide 상태 평가 방식 승계)

각 항목에 `유지 / 개정됨 / 신설 / 폐기 후보` 판정. 판단 기준:

- 최근 1개월 내 실제 사용 여부 (기억 + git log + 세션 이력)
- 팀 운영 규칙(ways-of-working)과 충돌 여부
- 더 나은 대체재 등장 여부
- **패치 노트 3개 이상 누적 여부** — 규칙 변경을 주석 추가로 때운 문서는 본문과 모순되기 시작한다(2026-07-25 start 사례). 누적 시 "개정됨(리라이트 필요)" 판정

폐기 후보는 **즉시 삭제하지 않고** 레지스트리에 표기만 → 다음 audit에서도 미사용이면 그때 삭제 제안.

### 3-b. 스킬화·자동화 판단 4기준 (2026-08-27 신설 — 강의 S3 수용)

신설 후보든 검토 후보든, "스킬로 만들 가치가 있나"는 아래 4축으로 판정한다. 기준 없이 등재된 후보는 방치된다(E-8 사례).

| 축 | 질문 | 판정 |
|---|---|---|
| 반복 빈도 | 주 1회 이상 같은 형태로 반복되나 | 아니면 스킬보다 프롬프트 한 번이 싸다 |
| 입출력 정형성 | 입력 위치·출력 형식이 정해져 있나 | 정해져 있으면 동적 주입(느낌표+백틱 문법, `` ! `명령` `` 형태 — 붙여 쓰면 로드 시 실행됨) + 출력 형식 고정 |
| 검증 가능성 | 결과를 기계적으로 확인할 수 있나 | 테스트·diff·목록 비교가 가능해야 무인 실행, 아니면 사람 판단 단계를 남긴다 |
| 실패 비용 | 틀렸을 때 되돌리기 쉬운가 | 크면 `disable-model-invocation: true`(사람만 호출) + 승인 단계 |

조합: 정형·검증 가능 → 스킬 자동 실행 / 정형·실패 비용 큼 → 스킬 + 사람 승인 / 비정형·검증 가능 → 서브에이전트 조사 → 사람 판단 / 비정형·검증 어려움 → 자동화 보류(보조만).

**스킬 작성 원칙 점검(기존 스킬 개정 시)**: description 첫 문장에 트리거 / 본문은 지시만·서사(왜)는 `reference/`로 / 계산·변환은 `scripts/` / 중요 지시 상단(컴팩션 재주입은 스킬당 5,000토큰) / 검증 단계 포함. 인벤토리가 커지면 `/doctor`로 목록 컨텍스트 비용 확인.

**스킬 신설·개정 후 유닛 테스트 (2026-08-31 신설, 선택)**: 스킬 본문을 고친 뒤 "잘 될 것 같다"로 끝내지 않는다. **새 서브에이전트(대화 히스토리 없음)에 그 스킬만 주고 고정 입력으로 1회 실행** → 기대 산출물(레퍼런스)과 비교. 차이가 나면 스킬 본문이 자족적이지 않다는 뜻(작성자 머릿속 맥락에 기대고 있음). `context: fork` 스킬은 이 방식이 곧 실사용 경로라 필수. 강사 팁(비공식)이지만 우리 verification-before-completion 원칙(증거 없는 완료 주장 금지)의 스킬판이라 수용.

### 4. 트렌드 스캔 (선택 — 시간 여유 있을 때만)

웹서치 1회로 최근 뜨는 에이전트 스킬/방법론을 확인하고, 팀 배정 스킬(debugging, incremental 등)의 교체·보강 후보가 있으면 레지스트리 "검토 후보" 절에 메모. **즉시 도입하지 않는다** — 후보 등재까지만.

🔴 **등재할 때 반드시 `판단: {시점}`을 붙인다** (2026-08-19 — "다음 audit에서 판단"만으로는 날짜가 없어 한 달째 방치되는 후보가 생겼다: E-8 07-25 등재 후 미판단). 시점은 **새 감시를 만들지 않고 이미 도는 트리거에 앵커**한다:

| 후보 성격 | 판단 시점 (앵커) |
|---|---|
| 특정 태스크·배분에서 써볼 것 (파일럿) | **그 태스크의 `/start`/브리프 작성 시** — 팀장이 브리프 쓸 때 REGISTRY 검토 후보 중 걸린 것을 확인 |
| 측정·관찰이 필요한 것 | **측정 기간 종료일** 명시 (예: model-guide 08-26) |
| 방향성·구조 변경 | **다음 스프린트 종료 성찰** (= 다음 audit) |
| 조건부 (어떤 사건이 나면) | 조건 + **조건을 감지할 사람·시점** 명시. 감지 장치 없는 "조건부"는 등재하지 않는다 |

**판단 시점이 지난 후보는 audit 때 반드시 결정한다** — 도입 / 폐기 / 시점 재산정(1회만, 사유 기록) 셋 중 하나. 두 번 연속 재산정이면 폐기.

**상류 도입 스킬 diff 체크**: provenance.md가 있는 스킬(예: verification-before-completion)은 상류 레포의 해당 파일과 diff — 갱신이 있으면 검토 후 원본 그대로 재도입(커스터마이징 금지 방침).

### 5. 산출물 갱신

1. `~/.claude/REGISTRY.md` 갱신 (스캔 일자 명기)
2. 팀 배정 변화가 있으면 `claude/skills/teamleader/skill-guide.md` 표도 동기화
3. 레포 파일(skill-guide 등) 변경분만 레포에 커밋 (REGISTRY는 개인 로컬 — 커밋 대상 아님)

## 가드레일

- **읽기 + 레지스트리 갱신만** — 이 커맨드가 스킬 파일 자체를 수정·삭제하지 않는다 (폐기는 별도 승인 후)
- **검토 후보는 `판단:` 시점 없이 등재하지 않는다** (4단계 표 참조). audit 시작 시 **판단 시점이 지난 후보부터** 처리한다
- 프로젝트 오버레이 스킬은 목록화만 — 내용 평가는 해당 프로젝트 소관
- 비개발 개인 스킬(가계부 등)은 이름만 등재, 레포 동기화 대상에서 제외 유지
