# issue-refine

담당 스토리의 description 구체화(배경·구현 범위·수락 조건) + **크기 판단 및 스토리 분할**.
완료된 스토리(PR 머지 시)에 구현 내용을 기록하고 상태를 전환하는 완료 처리도 담당한다.

## 언제 사용하나

| 모드 | 시점 | 트리거 |
|------|------|--------|
| **착수 전** | 개발 시작 전 | 스토리 내용이 비어있거나 모호할 때, 크기 판단이 필요할 때 |
| **완료 후** | **PR 머지 직후** | 스토리에 구현 내용 기록 + 상태 전환 |

스킬 실행 시 먼저 모드를 확인한다:

> "착수 전 스토리 구체화인가요, 완료된 스토리 기록인가요?"

인수로 힌트가 있으면(예: `done PROJ-421`, `완료 PROJ-421`) 모드를 자동 판단한다.

---

## 프로젝트 Config

**실행 첫 단계: 현재 프로젝트의 `.claude/team/tracker-config.md`를 읽는다** — 도메인·Cloud ID·프로젝트 Key·보드 ID·제품 개요·MCP/acli 전제가 거기 있다.
파일이 없으면 진행을 멈추고 사용자에게 안내한다: "이 프로젝트에는 tracker-config.md가 없습니다 — `.claude/team/tracker-config.md`를 만들어야 Jira 커맨드를 쓸 수 있어요" (템플릿: issue-cache 스킬 디렉토리의 `tracker-config.template.md` 복사).

**타입 분기**: `jira`면 아래 본문대로. `notion` — 착수 전 모드: 해당 백로그 페이지 본문을 3단계 템플릿 수준으로 구체화하고, 크기 상한 초과면 항목을 새 페이지로 분할한다 / 완료 후 모드: 구현 요약을 페이지 본문에 추가하고 상태를 `완료`로 전환한다. `local` — 같은 작업을 백로그 파일 항목에 직접 한다. ADF·스프린트·이슈 링크 절차는 jira 타입 전용.

## [착수 전 모드] 스토리 구체화 + 분할

### 1. 스토리 Key 입력

사용자에게 확인:
- 처리할 스토리 Key (예: `PROJ-356`) — 여러 개면 쉼표 구분

여러 개인 경우 순서대로 하나씩 처리한다.

### 2. 스토리·상위 이슈 조회

각 스토리에 대해:

1. **로컬 캐시 우선**: `.claude/stories/PROJ-{n}.md`가 있으면 먼저 읽는다. 캐시가 없거나 사용자가 "Jira가 바뀌었다"고 알린 경우에만 `getJiraIssue`로 조회 (`description`, `summary`, `parent`, `assignee` 포함).
2. 상위 이슈(Epic / Initiative)가 있으면 해당 이슈도 조회 → 목표·맥락 파악
3. 기존 description 확인:
   - 내용이 있으면 → **유지 / 수정 / 흡수** 중 사용자와 결정
   - 비어있으면 → 바로 초안 작성

### 3. Story Description 초안 작성

아래 템플릿으로 초안을 작성한다 (사용자에게는 **마크다운**으로 제시):

```
## 배경
{이 스토리가 왜 필요한지 — 상위 에픽/이니셔티브 목표, 해결하려는 문제}
{제품 개요의 핵심 기능 및 통합 맥락과 연결}

## 구현 범위
- 포함: {이번에 구현할 것 — 구체적인 기능/화면/API/컴포넌트}
- 제외: {명시적으로 이번 범위 밖인 것 — 있는 경우만}

## 수락 조건
- {검증 가능한 조건 1 — "~하면 ~가 된다" 형태}
- {검증 가능한 조건 2}
- ...
```

컨텍스트 우선순위: 상위 에픽 description > 제품 개요 > 이슈 summary

수락 조건 중 결정이 필요한 항목은 사용자와 논의 후 확정.

초안을 사용자에게 제시 → 승인 시 Jira 푸시, 수정 요청 시 반영 후 재확인.

**Jira 푸시 시 `contentFormat: "adf"` + ADF JSON 사용**. 수락 조건은 반드시 `taskList`/`taskItem`으로 작성해야 Jira에서 체크박스로 렌더링됨.

> ⚠️ `contentFormat: "markdown"` + `- [ ]` 는 Jira에서 체크박스로 렌더링되지 않음. ADF만 가능.

ADF 구조 예시는 이 스킬 폴더의 `adf-example.md` 참조 (heading·bulletList·taskList 전체 구조).

### 4. 크기 판단 → 스토리 분할

구현 범위가 확정되면 크기를 판단한다. **불변식: 스토리 1개 = PR 1개 = 브랜치 1개 = 에이전트 1명.**

#### 분할 기준 — 하나라도 해당하면 분할

1. 예상 변경 **400줄 초과** (생성물·lockfile 제외 — PR 크기 상한)
2. 에이전트 1명이 **2일 내 완료 불가**
3. **BE·FE 양쪽 다 무거움** (한쪽만으로 400줄에 근접)

해당 없으면 "분할 없이 진행해도 되는 크기입니다"라고 안내하고 5단계를 건너뛴다.

> **Sub-task는 만들지 않는다** — PR·브랜치·기록 단위에서 제외됨. 작업 항목을 남기고 싶으면 스토리 description 안 체크리스트로만.

#### 분할 방법

- **수직 우선**: 독립적으로 동작·검증 가능한 기능 조각으로 나눈다
- 안 되면 **기술 분할** 허용 (API/UI, 스키마/로직 등) — 단 반드시 에픽 또는 이슈 링크로 묶는다
- **원본 스토리는 첫 조각으로 범위 축소**(description 수정), 나머지 조각은 새 스토리로 생성
- 각 조각이 자기 배경·구현 범위·AC를 가진다 — 공통 AC를 복사하지 말고 해당 조각 것만

분할안을 표로 사용자에게 제시:

```
| # | 스토리 | 범위 | 예상 크기 | 의존성 |
|---|--------|------|----------|--------|
| 1 | PROJ-{n} (원본, 범위 축소) | ... | ~300줄 | - |
| 2 | (신규) ... | ... | ~250줄 | #1 머지 후 |
```

사용자 확인 후 추가·삭제·수정 반영 → Jira 반영.

### 5. 분할 스토리 Jira 반영

사용자 승인 후, 한 번의 세션에서 일괄 처리:

1. **원본 스토리**: `editJiraIssue`로 범위 축소된 description·AC 반영 (3단계 ADF 형식)
2. **새 스토리**: `createJiraIssue`로 생성
   - **issuetype**: `스토리`
   - **parent**: 원본과 같은 에픽 (있는 경우)
   - **sprint**: 원본과 같은 스프린트 (다음 스프린트로 미룰 조각은 사용자와 결정)
   - **description**: 각자의 3단계 템플릿 (ADF)
3. **링크**: 에픽으로 안 묶이는 경우 `createIssueLink`로 원본과 연결 (`getIssueLinkTypes`로 사용 가능한 타입 확인 후 "relates to" 등)

### 6. 완료 안내

각 스토리 처리 완료 후 출력:
- Story Key + URL (분할했으면 전체 목록 + 의존성 순서)
- 캐시 갱신 안내: `/issue-cache {키들}` 재실행
- 다음 단계: "각 스토리 = 브랜치 1개 = PR 1개로 진행, 의존성 순서대로 머지"

## [완료 후 모드] 스토리 구현 내용 기록 (PR 머지 트리거)

### C1. 스토리 Key 입력

사용자에게 확인:
- PR이 머지된 스토리 Key (예: `PROJ-421`) — 여러 개면 쉼표 구분(같은 날 다건 완료는 세션 말미에 배치 처리), 대화 컨텍스트에 이미 있으면 그대로 사용

### C2. 스토리 조회

`getJiraIssue`로 스토리 조회:
- `summary`(제목), `description`(기존 내용), `status`(현재 상태) 파악

### C3. 구현 내용 초안 작성

대화 컨텍스트(git diff, 코드 변경 내용, PR 번호 등)에서 구현 내용을 파악하거나, 사용자에게 직접 입력 요청.

아래 형식으로 초안을 작성해 사용자에게 제시:

```
## 구현 내용

**PR**: #{번호} ({머지 커밋 SHA})

**변경**: `{파일 경로}` — {무엇을 변경했는지 한 줄}

**방식**: {왜 이 접근을 선택했는지 1~2문장. 대안 대비 이유나 트레이드오프 포함}
```

작성 원칙:
- "무엇을 바꿨나"는 한 줄로 끝낼 것 (코드 재현 불필요 — GitHub에 있음)
- 핵심은 **판단 근거** — 다른 방법 대신 이걸 선택한 이유
- 전체 5줄 이내 유지

### C4. Jira 업데이트 + 상태 전환

사용자 승인 후:

1. `editJiraIssue`로 스토리 description 업데이트:
   - `contentFormat: "markdown"` 사용
   - **기존 description 내용은 유지**하고 뒤에 append, 구분선(`---`)으로 분리

```
{기존 description 내용}

---

## 구현 내용

{작성한 내용}
```

   기존 description이 비어있으면 구분선 없이 바로 작성.

2. 상태 전환: `getTransitionsForJiraIssue`로 가능한 전환 확인 → `transitionJiraIssue`로 완료 상태로 전환. (팀 규칙상 배포 후 확인이 남았으면 "리뷰/검증" 단계까지만 — 사용자와 확인)

### C5. 완료 안내

- 스토리 Key + Jira URL + 전환된 상태
- AC 최종 체크는 배포 후 **사용자가 직접**

## 가드레일

**공통**
- Jira 이슈 수정·생성은 반드시 **사용자 확인 후** 실행
- issuetype 오류 시 `getJiraProjectIssueTypesMetadata`로 먼저 확인

> ⚠️ **[매우 중요] description에 이미지가 있을 때 업데이트 절차**
>
> MCP를 통해 description을 수정하면 **기존 인라인 이미지가 반드시 깨집니다.**  
> (blob URL을 API로 재전송 시 MCP가 `type=external`로 변환하여 미디어 참조가 깨짐)
>
> **이미지가 있는 이슈를 업데이트하기 전에 반드시 다음을 안내하고 확인받을 것:**
>
> "이 이슈의 description에 이미지가 포함되어 있습니다.  
> API를 통해 수정하면 이미지가 깨지므로, 지금 **이미지를 캡처 또는 다운로드**해 두세요.  
> 업데이트 후 Jira UI에서 직접 재첨부해야 합니다. 진행할까요?"
>
> 사용자 확인 후 업데이트 진행. 업데이트 완료 후 이미지 재첨부 필요 여부를 재안내할 것.

**착수 전 모드**
- **Sub-task 생성 금지** — 크기 초과의 대응은 스토리 분할뿐
- 분할 시 각 스토리가 **자기 AC만** 가진다 — 공통 AC 중복 복사 금지
- description 푸시 시 `contentFormat: "adf"` + ADF JSON 객체 사용 — 수락 조건 체크박스는 ADF `taskList`/`taskItem`만 렌더링됨
- `contentFormat: "markdown"` + `- [ ]` 는 체크박스로 렌더링 안 됨 (Jira 제약)
- 분할 후 로컬 캐시(`.claude/stories/`)가 stale — 재캐시 안내 필수

**완료 후 모드**
- 기존 description **덮어쓰기 금지** — 반드시 append
- 구현 내용은 **최대 10줄** (코드 블록 포함) — 간결하게
- Story AC 체크는 자동화하지 않음 — 배포 후 사용자가 직접 수행

## 다른 프로젝트로 전환 시

그 프로젝트에 `.claude/team/tracker-config.md`만 새로 작성하면 재사용 가능 (커맨드 수정 불필요).
