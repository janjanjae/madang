# start

새 스토리/에픽 착수 오케스트레이션 — Phase 설계 + PROGRESS.md 초기화.
**팀장 전용** (PROGRESS.md 초기화 = 허브 문서 작성. 팀원 사용 금지 — skill-guide 참조).

> 2026-07-26 리라이트: 구 모델표(glm-5.2·Pro 플랜 전제)·`/jira-story-fetch` 참조·"새 세션 붙여넣기 프롬프트" 패턴 제거 — 각각 model-guide.md, `/issue-fetch`, 파일 기반 브리프(2026-07-14 전환)로 대체.

## Step 1: 상황 파악 + 소스 선택

**착수의 단일 진입점은 이 커맨드다** — 아래 조회·캐시는 이 단계가 내부에서 실행하므로 사용자가 다른 커맨드를 따로 칠 필요 없다.

다음을 사용자에게 물어보거나 인자로 받아라:
- **Jira 스토리 번호** (`.claude/team/tracker-config.md` 타입 `jira`): `/issue-fetch {KEY}-{n}`으로 캐시 생성 후 `.claude/stories/{KEY}-{n}.md`를 읽는다. description·AC가 비면 `/issue-refine` 착수 전 모드를 먼저 안내.
- **GitHub 이슈 번호** (`.claude/team/tracker-config.md` 타입 `github`): `/issue-fetch {번호}`로 캐시 생성 후 `.claude/stories/{번호}.md`를 읽는다. Description·수락 조건이 비면 `/issue-refine` 착수 전 모드를 먼저 안내.
- **개인 백로그 후보** (사용자 스킬 `backlog-check`가 있으면): 이 프로젝트의 inbox·검토됨 항목을 조회해 "이번 착수에 같이 태울 후보"로 제시하고, **사용자가 고른 것만** 계획에 반영 (고른 항목은 상태 `티켓화`로). 스킬이 없는 환경이면 조용히 생략.
- **소스 기본값** (가용성은 tracker-config의 타입이 결정, 이번 회차 포함은 실행 시 선택): 타입 `jira`/`github`는 **기본 트래커만** — 백로그 후보는 사용자가 요청할 때만 조회 (착수마다 노션 MCP 토큰 지출 방지). 타입 `notion`/`local` 또는 config 없음은 **기본 백로그**가 주 소스.
- 둘 다 없으면: 지금 하려는 작업이 뭔지 간단히 설명 요청.

## Step 2: 작업 성격 판단

| 유형 | 설명 | Phase 구성 |
|------|------|-----------|
| 신규 개발 | 없던 기능을 처음 만드는 것 | 설계 → 구현 → 검증 |
| 기존 코드 수정/개선 | 있는 코드를 변경하는 것 | **분석 → 설계 → 구현 → 검증** |
| 버그 수정 | 특정 에러/버그 해결 | 분석 → 구현 → 검증 |
| 단순 변경 | 설정, 텍스트, 소규모 수정 | 구현 → 검증 |

## Step 3: Phase별 목표 구체화

- **분석**: 어떤 코드를 읽어야 하는지, 파악해야 할 핵심 질문이 뭔지
- **설계**: 어떤 결정을 내려야 하는지, 태스크를 어떻게 쪼갤지 (`planning-and-task-breakdown` 활용)
- **구현**: 어떤 순서로 무엇부터 만들지 — **팀원 배분 단위**로 (병렬 가능하면 파일 경로가 안 겹치게 분리)
- **검증**: 완료 기준이 뭔지 (자동 검증 vs 사용자 직접 확인 항목 분리)

## Step 4: 모델·팀원 배분 전략

- 모델 배분은 `~/.claude/skills/teamleader/model-guide.md`가 SSOT — Phase별 권장 모델을 이 문서 기준으로 제안 (이 커맨드 안에 모델표를 두지 않는다: 이중 관리 방지).
- 팀원 배분은 `roster.md` 기준: 일반 구현·병렬 물량 → 몽글(분신), 핵심·까다로운 슬라이스 → 번뜩, UX 시안 → 슥슥.

## Step 5: Phase별 브리프 초안 생성

각 Phase의 구현 태스크를 **팀원 브리프 초안**으로 작성한다 (배분 시 `.claude/team/briefs/{인스턴스}.md`로 전달 — 자기완결 원칙, ways-of-working "브리프" 절 참조).

브리프에 반드시 포함:
- **머리에 작업 지시 5요소 고정 헤더** — `[목표]`(바뀐 뒤 상태 한 문장) `[범위]` `[제약]`(건드리지 말 것) `[완료 기준]` `[보고]` (ways-of-working "태스크·브리프" 절의 템플릿, 2026-08-27). 모르는 값은 `TBD`.
- 전체 작업 배경 (한 문단) + "왜 지금 이것부터"
- 이 태스크의 목표와 완료 기준 (AC 수준으로 구체적으로 — 실제 값)
- 구체적으로 봐야 할 파일/모듈 (절대경로)
- 산출물 + 보고 양식, 권장 프로바이더·모델, 컨펌 생략 여부

> 팀 워크플로우 없이 혼자 진행하는 예외 세션에서는 브리프 초안을 그 세션의 작업 계획으로 그대로 쓰면 된다.

## Step 6: 프로젝트 구조 스캐폴딩 + PROGRESS.md 초기화

**팀 구조가 없는 프로젝트라면 먼저 폴더를 세운다** (이미 있으면 무해하게 통과):

```bash
mkdir -p .claude/team/briefs .claude/team/confirm .claude/team/reports
```

- `briefs/` — 팀장이 워커에게 배분하는 브리프 파일
- `confirm/` — 컨펌 신호(request/reply) 교환
- `reports/` — 팀원별 보고 파일 (팀원 세션이 기력회복 시 읽는 자리)

> 애든덤(`.claude/team/agents/`)·프로젝트 트래커 설정(`.claude/team/tracker-config.md`)은 필요 시점에 생성 — 부트스트랩 단계에서 강제하지 않는다.

**허브 문서 아카이빙 (초기화 전에)**: 기존 TASKS.md/PROGRESS.md에 "대체됨"·"이력 보존" 표시 블록이나 지난 스토리/스프린트 블록이 있으면 `.claude/archive/TASKS-archive.md`·`PROGRESS-archive.md`로 원문 그대로 이동한다 (없으면 생성. 이동분 앞에 `## [YYYY-MM-DD 이동분]` 헤더, 원본 상단에 `> 과거 이력은 .claude/archive/ 참조` 포인터 유지). 요약·재작성 금지 — 순수 이동만. 애매하면 유지. 새 착수 시점이 구 블록이 "지난 것"이 되는 경계라 여기서 정리한다 (세션 중 롤링은 `/checkpoint` 소관).

그다음 `.claude/PROGRESS.md`를 이 작업 기준으로 초기화하라. TASKS.md 태스크 목록도 함께 설계(`planning-and-task-breakdown`).
