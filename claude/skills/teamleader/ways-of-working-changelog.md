## 2026-08-24 — 감시를 `Bash(run_in_background)` → `Monitor(persistent)`로 교체

**사용자 진단 요청**: *"너가 자꾸 워커들 컨펌을 바로 못 받고 있어. 하나 확인하면 나머지 워커들을 확인하지 않는 걸까?"*

**측정으로 원인 특정** — 가설("하나만 보고 나머지를 안 본다")은 **틀렸다.** 감시 스크립트는 `*.request.md` 전체를 루프로 돈다. 실제 원인은 **감시가 살아 있지 않은 시간대**였다:

|---|---|---|---|
| 꼬부기 1차 | 14:28 | 14:32 | ✅ 4분 (감시 작동 중) |
| 메타몽 | 15:26 | 15:47 | 🔴 21분 |
| 꼬부기 2차 | 15:28 | 15:54 | 🔴 26분 |

**공백 4원인**: ①`run_in_background`는 exit할 때만 알림 → 1회용 ②🔴 감시를 *"컨펌 OR PR 머지"*로 섞어서, **15:16 머지 발화 때 컨펌 감시가 같이 죽었다**(이후 40분 무방비, 컨펌 3건 적체) ③재무장이 별도 스텝이라 reply 쓰는 동안 잊는다 ④타임아웃 후 자동 재개 없음.

**사고**: 같은 날 오후 팀장이 6-B를 신설해놓고, 몇 시간 뒤 **949(PR #292)를 로컬 스모크 없이 발행 지시**했다. reply에 *"발행해라 → 발행 후 Preview 스모크"*라고 썼는데, 949는 **최초 발행**이라 로컬이 선행이어야 했다. 사용자가 *"우리 순서상 로컬 스모크 완료 후 PR 올리는 거 아닌가?"*로 잡아냈고 Draft 전환(`gh pr ready 292 --undo`)으로 복구.

**사용자가 제시한 개선안 (채택)** — Draft를 게이트로 쓰면 두 스모크를 다 하면서도 리뷰어 노출이 없다:

```
① 로컬 스모크 → ② PR Draft 발행 → ③ CI 후 Preview 스모크
→ ④ Draft 해제 + 리뷰 요청 → ⑤ 승인 후 main 재머지 → ⑥ 머지
```

초판보다 나은 점: 초판은 로컬과 Preview를 **택일**로 놨는데, 실제로 둘은 **보완재**다(로컬=발행 전 방어, Preview=환경 충실도). Draft가 그 둘을 한 흐름에 넣는다.

**추가**: *"발행 지시 전 최초/반영분을 한 줄로 판정하라"*를 명시. 판정이 없으면 규칙이 서술로만 남고 발동하지 않는다.

> 오늘 세 번째 "아는 규칙을 어긴" 사례다(B-1 스코핑 · REGISTRY 미확인 · 이번 건). 공통점: **규칙은 알고 있었으나 그 순간 판정 스텝이 없었다.** 규칙에는 반드시 *"언제 무엇을 확인하라"*는 행동이 붙어야 한다.
