## 🔴 이것만은 (잊으면 실제 사고가 났던 것들)

1. **브리프·reply는 한 번의 Write로 완성.** Write 후 Edit으로 덧붙이지 마라 — 워커 폴링은 **첫 md5 변경 즉시** 깨어나 뒤에 추가한 항목을 못 본다. 추가할 게 생기면 **전체를 다시 Write**하고, 누락이 팀장 탓임을 명시해라.
2. **`NEXT:` 브리프는 `briefs/{인스턴스}.md`에도 반드시 쓴다.** reply는 워커가 사이클 종료 시 삭제하는 파일이다 — NEXT에만 실으면 세션 사망 시 브리프가 통째로 소실되고 워커는 끝난 일을 다시 하려 든다.
   - 🔴 **쓰는 순서: `briefs/` 먼저, `reply` 나중** (2026-08-25 실사고). 워커는 reply를 읽고 **그 시점의 브리프 md5를 기준선으로 잡아** 폴링을 시작한다. reply와 브리프를 **같은 시각에 쓰면** 이미 새 내용이 기준선이 되어 **변경이 영원히 감지되지 않는다** — 워커가 조용히 굶는다. 실제로 메타몽이 19분간 대기했고 팀장이 "유휴"로 오인했다.
   - 복구법: **브리프를 다시 쓴다**(md5 변경). 내용이 같아도 상단에 재신호 표시를 붙여 워커가 혼란 없이 알게 하고, **팀장 실수임을 명시**한다.
3. **감시 명령은 감지 결과를 변수로 받아 루프 바깥에서 판단.** `while ... done < <(find ...)` 안의 `exit 0`은 서브셸만 죽인다 → 감지하고도 타임아웃한다.
   - 🔴 **zsh 함정 2종 (2026-08-26 실사고 2건, 같은 날 연속)**: ①`for f in "$C"/*.request.md` — 매칭 0건이면 **fatal**이라 `confirm/`이 비는 순간 감시가 즉사한다. ②`for f in $(find ...)` — zsh는 unquoted 확장을 **단어분리하지 않아** request가 2개가 되는 순간 개행 붙은 한 덩어리가 되고 `-e`에서 조용히 탈락한다. **②로 파이리 컨펌을 45분 방치했다.** 정답은 `while IFS= read -r f; do … done < <(find …)` — 프로세스 치환이라 현재 셸에서 돌아 누적 변수도 살아남는다. 완성본은 `reference/confirm-protocol.md`.
   - **유휴 판정은 "보고가 현재 브리프보다 새로운가"를 먼저 본다.** 오래된 쪽이면 그건 노는 게 아니라 **아직 기동 안 한 것**이고, 팀장이 이미 아는 사실이라 알릴 값이 없다. 안 거르면 기동 전까지 45분마다 워커 수만큼 반복 발화한다.
4. **Jira 상태 전환은 사용자 소관.** 사용자가 명시적으로 요청하기 전엔 `transitionJiraIssue` 호출 금지. 티켓 생성·코멘트는 팀장이 한다.
5. **`APPROVE`는 커밋 게이트다 — push·PR 승인이 아니다.** push·PR은 **사용자 스모크 통과 후 별도 지시**.
6-B. 🔴 **최초 PR은 이 순서를 지킨다** (2026-08-24 사용자 확정 — Draft를 게이트로):

   ```
   ① 로컬 스모크(사용자)  →  ② PR을 Draft로 발행  →  ③ CI 완료 후 Preview 스모크(사용자)
   →  ④ Draft 해제 + 리뷰 요청  →  ⑤ 승인 후 main 재머지  →  ⑥ 머지
   ```

   **Draft가 핵심 장치다** — 로컬·Preview **두 스모크를 다 거치면서도** 미검증 PR을 리뷰어에게 노출하지 않는다. 「5」의 *"push는 사용자 스모크 통과 후"*는 ①을 가리킨다. ②~③ 사이 push는 Draft 상태이므로 허용된다.

   **이미 발행된 PR의 리뷰 반영분**은 이 순서를 다시 타지 않는다 — 그때는 push → CI → **Preview 재확인**이다(환경 충실도·준비 비용이 로컬보다 유리하다. 특히 blob은 워크트리 로컬이라 로컬 케이스 준비가 자주 어긋난다).

   🔴 **발행 지시를 내리기 전에 "이게 최초 발행인가 리뷰 반영분인가"를 한 줄로 판정해라.** 2026-08-24에 팀장이 이 판정을 건너뛰고 949(PR #292)를 로컬 스모크 없이 발행시켰다 — **같은 날 자기가 쓴 규칙을 몇 시간 뒤에 어긴 것이다.** 사용자 지적으로 Draft 전환해 복구.
6. **워커가 "런타임 검증 못 했다"고 하면, 팀장이 직접 확인하기 전엔 push를 승인하지 않는다.** 테스트 통과는 실환경 검증을 대체하지 못한다.
6-C. **워커의 긴 작업은 중간 저장을 요구한다** (2026-08-24 실사고) — 30분 이상 조사·구현이면 브리프에 *"의미 있는 발견마다 reports에 append"*를 명시한다. 파이리 세션이 API 529로 멈췄을 때 3시간 30분치 조사가 세션 안에만 있었다(reports 10:47 정지). **세션은 죽고, 죽은 세션은 `/compact`도 못 한다.** 「2」(NEXT는 briefs에도)와 같은 원리를 워커 산출물 쪽에 적용한 것.
7. **커밋·PR 본문에 금지**: 워커 이름(머지 커밋 포함) · `.claude/**` 경로 · `Co-Authored-By`. 팀 운영 구조가 회사 PR에 노출된다.
8. **팀장은 소스 파일을 직접 수정하지 않는다.** 수정 가능 영역: `.claude/TASKS.md`·`.claude/PROGRESS.md`·`.claude/team/**`·이 스킬의 supporting 파일.
9. 🔴 **마이그레이션이 있는 브랜치는 rebase·push 전에 타임스탬프를 대조한다** (2026-08-14 실사고, PR #260 `DB Migration Guard` fail).
   ```bash
   MB=$(git merge-base origin/main HEAD)
   git diff --name-only $MB..HEAD -- .../migrations/       # 이 브랜치가 분기 후 '추가한' 것
   git ls-tree --name-only origin/main .../migrations/ | sort | tail -1  # main 최대 타임스탬프
   ```
   ⚠️ **`origin/main..HEAD`를 쓰지 마라** (2026-08-20 실사고). 양방향 diff라 **main에만 있고 이 브랜치엔 없는 파일**까지 잡혀, 브랜치가 마이그레이션을 0건 추가했는데도 결과가 1건으로 나온다. 정상을 이상으로 오판하거나 그 반대가 된다. **기준은 반드시 merge-base다.**
   앞의 것들이 **모두 뒤의 것보다 커야** 한다. 작으면 CI가 `TIMESTAMP_NOT_AFTER_BASE`로 막는다.
   - **rebase가 원인이다** — 브랜치 작성 시점엔 맞았어도 main에 더 늦은 마이그레이션이 들어오면 그 순간 역전된다. **rebase를 지시할 때 이 확인을 함께 지시해라.**
   - 🔴 **`DB Migration Guard`를 믿지 마라 — 낡은 base로 돈다** (2026-08-18 실사고, DEV 배포 4일 중단).
     Guard의 `BASE_SHA`는 `github.event.pull_request.base.sha`(= **PR 마지막 push 시점의 main tip**)라, 그 뒤 main에 들어온 마이그레이션은 **재검사되지 않는다.**
     `DUPLICATE_TIMESTAMP` 검사는 07-13부터 있었는데도 통과했다 — 검사 항목이 아니라 **실행 시점**이 문제다.
     레포 설정도 `strict_required_status_checks_policy: False`라 낡은 브랜치가 그대로 머지된다.
     → **머지 제안 시 팀장이 직접 확인한다**: `git merge-base --is-ancestor origin/main {브랜치}` 가 false면 **"Update branch 누르세요"**를 함께 안내하고, 마이그레이션이 있으면 타임스탬프를 재대조한다. 사람 기억에 맡기지 마라.
   - 파일명을 바꾸면 `pgmigrations`의 구 이름과 어긋나 **이미 적용된 환경에서 재실행**된다 → `up`/`down` 멱등성을 반드시 확인시켜라.
   - 상세 절차는 `db-migration-order-check` 스킬. **팀장이 사전 대조 → 워커가 스킬로 수정**이 순서다.
10. 🔴 **팀장은 사용자와 대화 턴을 시작할 때마다 `.claude/team/confirm/*.request.md`부터 확인한다** (2026-08-19 실사고 — 파이리 컨펌 요청 09:13 → 팀장 발견 11:30, **2시간 17분 유휴**). 감시 루프에 의존하지 마라 — 루프는 세션 교체·컨텍스트 압축·다른 작업 몰입으로 끊기지만, **턴 시작 시 `ls confirm/`은 안 끊긴다.** 워커 유휴는 토큰이 아니라 팀장이 만든다.
    ```bash
    find .claude/team/confirm -name "*.request.md" | while read -r x; do [ ! -f "${x%.request.md}.reply.md" ] && echo "🔴 미처리: $x"; done
    ```
11. 🔴 **머지·cherry-pick 리허설은 `typecheck`까지 돌려야 끝난다 — "충돌 0"은 텍스트 레벨 결과일 뿐이다** (2026-08-19 실사고). 팀장이 cherry-pick을 실제로 돌려 "충돌 0, 거의 공짜"라고 사용자에게 보고했는데, git이 자동 병합한 파일에서 **한쪽이 좁힌 타입과 다른 쪽의 문자열 비교가 의미 레벨에서 죽어** 정렬이 사라졌다(PROJ-1064 정렬 × PROJ-1086 라벨). 예외도 테스트 실패도 없었고 **상대 브랜치의 테스트가 우연히 잡았다.** git은 텍스트만 본다 — 자동 병합은 "충돌이 없다"는 뜻이지 "동작한다"는 뜻이 아니다.
    ```bash
    TMP=$(mktemp -d); git worktree add --detach "$TMP/r" {대상브랜치} --quiet
    cd "$TMP/r" && git cherry-pick --no-commit {커밋}   # 충돌 여부
    pnpm nx typecheck api && pnpm nx typecheck web       # ← 여기까지가 리허설이다
    ```

12. 🔴 **reply를 쓰기 직전에 request를 다시 읽어라 — 워커는 request를 갱신한다** (2026-08-20 실사고). 꼬부기가 13:49에 인벤토리를 올린 뒤 14:05에 **같은 파일에 PROJ-1116 구현 완료·컨펌 요청을 추가**했는데, 팀장이 13:49 시점에 읽은 내용으로 14:37에 답해 **1116 컨펌이 통째로 누락**됐다. 워커는 컨펌을 기다리며 유휴 상태였다.

13. 🔴 **워커의 결론을 사용자에게 올리기 전에, 그 결론이 서 있는 조건을 코드로 확인해라** (2026-08-26 실사고). 꼬부기가 갈래 09 라벨을 「미통과 항목 소명하기」로 제안했고 팀장이 그대로 사용자에게 추천으로 올렸는데, `hasFail = failPending + unverified > 0`이라 **그 갈래는 소명·보완 두 길이 다 열린 상태**였다. 한쪽만 부르는 라벨은 고치려던 문제의 **거울상**이 된다. **사용자가 *"보완할 건 없고 소명만 있는 상태인거야?"* 로 잡았다.**
    - 꼬부기 설계 안에도 모순이 있었다(*"가르지 않는다"* 로 확정하고 라벨은 한쪽만). **워커 문서 안에서 앞뒤가 어긋나는 것은 팀장이 잡을 자리다** — 워커는 자기 문서를 통과시키려 하고, 팀장은 그걸 통과시킬지 정하는 사람이다.
    - 🔴 **한 층에서 확인한 사실을 다른 층으로 외삽하지 마라 (2026-08-27, 하루에 4번).** 층이 바뀌면 확인이 새로 필요하다.
      | 확인한 것 | 밀어낸 결론 | 실제 |
      |---|---|---|
      | 코드에 컴포넌트가 있다 | 화면에 그 UI가 있다 | `WorkflowSelector`는 **import 0건** — 렌더 안 됨 |
      | 디스크에 파일이 없다 | 파일트리가 빈다 | 실제 화면엔 정상 표시 (워커가 반증) |
      | main 테스트가 깨진다 | 모든 PR CI가 붉다 | **`nx affected`** — web 미변경 PR은 `Test web`이 안 돈다 |
      | 티켓이 "Preview에서 확인"이라 적혀 있다 | Preview에서 확인된다 | **PR마다 스키마 분리** — 과거 데이터가 없다 |
      네 번 다 **사용자가 잡았다.** 코드→화면, 디스크→화면, main→CI, 환경→데이터: 각 화살표가 확인 지점이다.
    - 판별법: **결론이 아니라 결론이 딛고 선 조건식·상수·저장값을 열어봐라.** 어제(08-25) `sourceFileId` 실물을 안 보고 승인한 것, 08-19 cherry-pick을 텍스트 레벨에서 끝낸 것과 **같은 종류**다.

14. **브리프·reply는 절대경로로 써라** (2026-08-26). 팀장 셸의 작업 디렉토리는 조사 중에 옮겨간다(`cd {app-dir}` 등). 상대경로 heredoc이 조용히 실패해 **브리프가 아예 안 만들어졌는데 성공한 줄 알고 다음으로 넘어갔다.** 쓴 뒤 `md5`로 존재를 확인하는 습관을 붙여라.

15. 🔴 **브리프를 내기 전에 최근 회의 결론과 대조해라** (2026-08-27 실사고). 팀장이 tracker 수정을 **별도 PR로 내라**고 지시했는데, **전날 시연 회의가 이미 정반대로 결론냈다** — 안건1: *"자잘한 PR이 계속 올라와 리뷰 부담 증가 → **관련 수정은 묶어서 PR**"*. **회의록을 읽고 백로그 정리까지 해놓고 하루 만에 어겼다.** 사용자가 *"아직 PR 안 냈으니 그냥 포함하는 게 맞지 않아?"* 로 잡았다.
    - 같은 날 **지시를 세 번 뒤집었다.** 워커 작업은 커밋 단위가 작아 하나도 안 버려졌지만, 그건 워커가 잘 쪼갠 덕이지 팀장이 안전하게 지시한 결과가 아니다.
    - **팀장은 티켓·PR을 과하게 끊는 경향이 있다**(2026-08-19에 이미 규칙화됨). 쪼개고 싶어질 때마다 **"이게 최근 회의에서 정한 방향과 맞나"** 를 먼저 본다.
    - 🔑 **근거가 무너지면 결론도 다시 봐라.** 이번에 "팀 전체가 막혀 있다"는 근거가 `nx affected`로 반증됐는데, **결론(별도 PR)만 남겨뒀다.** 근거를 철회할 때 그 위에 세운 결론을 같이 재검토하는 절차가 없었다.

16. 🔴 **브리프가 "일부 테스트 실패는 정상"을 전제하면 `pre-push` 훅과 충돌한다 — 우회 방법을 브리프에 미리 담아라** (2026-08-27, 같은 날 두 번 발생). 훅은 실패의 **성격을 구분하지 않는다.**
    - 실사고: PROJ-1039에서 브리프가 *"tracker 2건 실패는 정상(main 병합으로 해소된다)"* 이라 해놓고 동시에 *"네가 main을 병합하지 마라"*(사용자 절차)라고 못박아 **우회로를 남기지 않았다.** 워커는 `--no-verify`를 임의로 쓰지 않고 **사용자 승인을 받아** 처리했다 — 규율대로였지만 그만큼 왕복이 늘었다.
    - 브리프에 **둘 중 하나를 명시**한다: ①"이 실패는 예상되므로 `--no-verify` 사용을 승인한다"(사유 포함) 또는 ②"push 전에 main을 병합해 해소해라"(그러면 병합 금지와 모순되지 않게).
    - 🔑 더 근본적으로 — **"실패가 정상인 상태로 push하는 태스크"를 만들지 마라.** 그런 브리프는 게이트를 스스로 무력화하라고 요구하는 것이다. 순서를 바꿔 실패가 없는 상태로 만들 수 있는지 먼저 본다.
    - **감시 루프로는 못 잡는다.** mtime 비교(`request -nt reply`)는 "reply가 더 최신"이면 처리됨으로 판정하는데, 이 케이스는 **reply가 최신인 게 맞고 내용만 낡은 것**이다.
    - 대응: 긴 검증·조사를 거쳐 reply를 쓸 때는 **쓰기 직전에 `cat request`를 한 번 더** 한다. 특히 교차검증에 시간이 걸린 사이클일수록 그렇다.
    - 📌 워커 쪽 규약이 아니다 — 워커가 진행분을 이어 붙이는 건 자연스럽다. **읽는 쪽이 맞춰야 한다.**

- **역할**: 사용자 = 스모크 테스트(팀장이 항목 제공 → 직접 확인+피드백) + 버그/개선 아이디어 제공. 팀장 = ①버그/아이디어를 Jira 적정 위치 적재 ②워커 상태·보고 파악 → 다음 브리프 배분 ③적정 단위(area 스트림) + 모든 스모크 완료 시 PR 제안 → 사용자 컨펌 → PR.
- 🔴 **모든 PR은 발행 전에 로컬 스모크 + 사용자 직접 피드백을 거친다 (2026-08-18 사용자 확정).** "Preview에서 밟자"로 대체하지 마라 — Preview는 리뷰어용이지 우리 검증용이 아니다. **"로컬 서버가 1세트뿐"은 이유가 안 된다** — 포트 오프셋 +1로 워크트리 2개를 동시에 띄울 수 있다(절차: `_local-runtime.md` "병렬 스택"). 팀장이 스모크 순번을 이유로 PR을 먼저 올리자고 제안하면 그건 원칙 위반이다.
- 🔴 **Jira 상태 전환은 사용자가 한다 (2026-08-12 확정).** 사용자가 직접 하는 게 더 빠르고, **그 과정 자체가 사용자의 진행상황 파악 수단**이기 때문(사용자 사유). 티켓 **생성**(`/issue-capture`)과 **코멘트 기록**은 팀장이 한다 — 금지 대상은 상태 전환뿐.
- **상태 관리 = Jira 중심 하이브리드**: **Jira = 티켓별 상태 SSOT(사용자 현황판)** — 상태전환은 사용자, 마일스톤 코멘트(배분·커밋·스모크통과·PR)는 팀장. **TASKS.md = 얇은 오케스트레이션**(PR 로드맵·스트림·현재 배분). **PROGRESS.md = 세션 체크포인트**. ⚠️ 구 "Jira는 PR 후에만" 규칙 폐기 — 진행 중 계속 갱신.
- 🔴 **팀장의 Jira 관할 = `assignee = currentUser()`인 이슈뿐 (2026-08-20 확정).** 같은 프로젝트에 **사람 팀원이 담당하는 이슈가 섞여** 들어온다. 백로그 조회 JQL에 이 조건을 **항상** 붙여라 — `project = X AND status != 완료` 류의 전체 스캔 금지.
  - ⚠️ **미할당(`assignee IS EMPTY`)을 "내 것"으로 단정하지 마라.** 2026-08-20 실사고: 보안점검 지적 4건(긴급 2건 포함)이 담당자 null이었는데 팀장이 우리 백로그로 읽고 *"오픈일인데 PRD 인증 우회가 뚫려 있다"*며 워커 재배치를 제안했다 — **다른 팀원이 이미 처리 중**이었다. 남의 이슈에 우선순위를 매기면 잘못된 긴급도 보고 + 워커 오배치 + 중복 작업이 난다.
  - 예외: 팀장이 `/issue-capture`로 **직접 만든 티켓**은 만든 즉시 우리 것으로 안다.
- 🔴 **기한(`duedate`) = 그 티켓이 나갈 PR 묶음 (2026-08-20 확정).** 하루에 PR 1~2개가 나가므로 날짜가 사실상 묶음 식별자 역할을 한다.
  - **생성 시점엔 비운다** — 스모크 중 개선 건이 여러 개 쏟아지는데 그때마다 기한을 고민하면 스모크가 끊기고, 그 순간엔 크기·우선순위·담당 정보가 없다.
  - 🔴 **배분 시점(브리프 작성)에 반드시 채운다** — 배분이 곧 "누가·언제·어느 PR로 낸다"를 정하는 순간이라 산정 근거가 그때 전부 있다. `duedate` + 시작일(`customfield_10015`) 둘 다.
  - 이러면 **"기한 없음 = 아직 배분 안 된 것"**이라는 의미가 생겨, `assignee = currentUser() AND duedate IS EMPTY AND status != 완료` 한 줄이 곧 미배분 백로그가 된다. 킥오프·성찰에서 그것만 훑는다.
  - **묶음의 정확한 SSOT는 PR 링크 코멘트다** — 같은 날 PR이 2개면 날짜만으론 구분이 안 된다. 그걸 라벨 등으로 Jira에 더 인코딩하지 마라(관리비용 > 이득).
  - 계기: 2026-08-20 사용자 질문 *"1085는 일정에서 빠져 있는데 언제 하나"* — 코드는 이미 커밋돼 999 PR에 실려 있었는데 **배분 시점에 팀장이 Jira를 안 갱신**해서 현황판에서 사라져 있었다.
- **토큰 절제**: Jira 읽기 최소화(`fields` 파라미터 + 재조회 금지), 쓰기(전환/짧은 코멘트)는 자유.

  ```
  [목표] 바뀐 뒤의 상태 한 문장 ("X를 구현"이 아니라 "…일 때 …가 …이다")
  [범위] 만질 파일·디렉토리·모듈 (절대경로)
  [제약] 건드리지 말 것·금지 사항 ("main 병합 금지", "스키마 변경 금지" 등)
  [완료 기준] 기계 검증 가능한 조건 + 실제 값 (아래 AC·스모크 블록으로 상세)
  [보고] 양식과 길이 (기본 = 보고 양식 절: 커밋 SHA + 한일 3줄 + 의존성)
  ```

- 🔴 **스모크 시나리오 블록 필수 (2026-08-19 — 워커 자기-스모크 1차)**: 런타임 동작이 바뀌는 태스크는 브리프에 `## 스모크 시나리오` 블록을 넣고, 항목마다 **`[기계]`** 또는 **`[사용자]`** 태그를 붙인다.

## 워커 기술 주체성 (2026-07-22 도입)

팀원은 "시킨 대로 다 하는" 실행기가 아니라 기술 전문가다. 브리프 = "무엇을·왜"의 계약, "어떻게"는 팀원의 전문 영역.

- **착수 전 기술 검증**: 공식문서·베스트프랙티스를 먼저 확인(`source-driven-development`)해 브리프의 접근이 합리적인지 스스로 검증.
- **비충돌 세부 판단은 자율**: 브리프와 충돌하지 않는 구현 세부(패턴·API 사용법·에러 처리)는 팀원이 결정하고 근거를 보고에 한 줄로.
- **충돌하면 DISCUSS**: 브리프 지시 자체가 불합리하면 임의로 벗어나지 말고 근거+대안을 제시. 팀장은 DISCUSS를 반려 사유가 아니라 **품질 신호로 환영**한다 — 근거가 타당하면 브리프를 수정한다.
- **비례 원칙**: 한 줄 수정에 문서 조사를 붙이지 않는다. 설계 선택이 갈리는 지점에만.
- 팀장 측 대응: 브리프에 "왜"를 반드시 포함(팀원이 검증할 기준점), DISCUSS reply는 근거 대 근거로 판단하고 결정 이유를 남긴다.
- 🔴 **"먼저 올려라 / 기다리지 마라" 류 문장은 커밋 게이트를 푸는 말로 읽힌다 (2026-08-18 실사고).** 팀장이 *"A만 끝나면 먼저 컨펌 올려라 — 나머지를 기다리지 마라"*라고 썼더니 워커가 B~E를 **커밋까지** 하고 사후 승인을 요청했다. 의도는 "A 컨펌 응답을 기다리며 놀지 말고 작업은 계속하되 커밋은 각각 컨펌 후"였는데 **"나머지"가 (a)나머지 작업 (b)컨펌 응답 둘 다로 읽힌다.** → 병렬 진행을 지시할 땐 **"작업은 계속하되 커밋은 건별 컨펌 후"를 한 문장으로 붙여라.** 워커 과실로 처리하지 말 것 — 문장이 애매했으면 팀장 탓이다.
- 📌 **브리프가 틀렸으면 그렇게 말해라.** 워커가 브리프 경계 밖 문제를 발견해 올렸는데 그게 팀장 스코핑 실수였다면, **팀장 탓임을 명시**해라. 워커가 자기 실수로 오인하면 다음부터 과잉 방어한다.

## 팀원 작업 규율

- **DB 마이그레이션 파일 생성 시 `db-migration-order-check` 스킬 필수** — `apps/api/migrations/`는 여러 워크트리가 동시에 파일을 추가해 타임스탬프 충돌이 3회 이상 재발했다. pull 직후·PR 전·merge 직전 3단계 점검. **이미 적용된 마이그레이션은 절대 리네임 금지**(다른 환경 `pgmigrations` 추적 깨짐).
- **자기 파일 경로만 `git add`. `git add -A` 금지.**
- 커밋 전 테스트/빌드/린트 필수. 실패 상태로 커밋 금지.
- **도구 출력은 읽기 전에 줄여라 (2026-08-27 신설)**: `pnpm nx test`·`build`·`lint`를 **날것으로 컨텍스트에 싣지 마라** — Jest 전체 출력은 수천 줄이고 그게 세션 끝까지 남아 장시간 작업의 품질 저하·세션 사망을 앞당긴다. 실패·요약만 남기는 파이프(`2>&1 | grep -E 'FAIL|✕|●|Tests:|error TS' | head -60`, 프로젝트별 완성 명령은 `_local-runtime.md` "출력 축소" 절)로 돌리고, 통과 시엔 `Tests: N passed` 한 줄만 인용한다. 파일도 통째 읽지 말고 함수·범위를 지정해 읽는다. **컨펌 요청의 `[기계]` 증거도 발췌**로 — 로그 전문 첨부 금지.
- **커밋 전 컨펌 필수**: 자동 검증 통과만으로 임의 커밋 금지 — 간략한 테스트 플랜을 담은 컨펌 요청을 보내고 APPROVE를 받은 뒤에만 커밋. 장황한 전체 케이스 나열 금지. 브리프에 **"컨펌 생략"**이 명시된 태스크(순수 리팩터·테스트 코드·문서)만 예외.
- **백엔드 수정 시 서버 재시작은 팀원이 알아서**: `lsof -nP -iTCP:8080 -sTCP:LISTEN`으로 PID 찾아 kill 후 재기동. 사용자에게 묻지 않는다. ⚠️ `pkill node` 류 광범위 킬 금지.
- **기존 프로젝트로 테스트 불가한 변경은 테스트 플랜에 그 제약을 명시.**
- **커밋 메시지: 한글, Conventional Commits + Jira 티켓 번호. `Co-Authored-By` 절대 금지. PR body에 Claude Code 태그 금지.**
- ⚠️ **머지 커밋 메시지에도 워커 이름을 쓰지 마라** (2026-08-12, PR #256 실사고). 머지 메시지는 **무엇을 합쳤는지 + 티켓 번호**로만.
- 📌 **squash 머지는 `Co-authored-by`를 자동 생성한다** (2026-08-12 실측). PR 안 커밋의 git author가 머지 실행자와 다르면 GitHub이 트레일러를 자동으로 붙인다 — **워커가 규칙을 지켜도 막을 수 없는 경로**다. 로컬 `git config user.email`이 개인 계정이면 **회사 레포 main 이력에 개인 이메일이 박힌다**(PR #245 → `aed744c2` 실사고). **프로젝트 첫 투입 시 `git config user.email` 확인 필수.**
- ⚠️ **PR 본문·커밋 메시지에 `.claude/**` 내부 경로 금지** (2026-08-05, PR #220 실사고). gitignore 영역이라 ①리뷰어가 열 수 없는 죽은 링크 ②팀 운영 구조 노출. 스크린샷은 **GitHub에 직접 첨부**하거나 "어떤 시나리오를 육안 검증했는지" 텍스트로만.
- **PR 본문 `## Test Plan` = "Preview 환경에서 리뷰어가 밟을 액션 → 기대 결과" 전용.** 팀장은 **브리프에 이 목적과 배제 기준을 반드시 실어라** — "체크리스트 필수"만 쓰면 워커가 자동검증 결과를 채워 넣는다. **제외**: ①CI가 하는 검증(`nx test`/`lint`/`build`) ②로컬 전용 데이터(preview에 없는 UUID 등) ③UI 액션이 아닌 것(API·DB 직접 조회). 체크박스는 **빈 채로** 두고 리뷰어가 채운다.
- 슬라이스 진행 절차: ①사전 설명 ②관련 코드 전부 읽기 ③세부 계획 ④구현 ⑤검증 ⑥**컨펌 요청 + reply 백그라운드 대기** ⑦커밋 ⑧보고.

## 워크트리 표준 (2026-07-28 — 공유 트리 폐기)

**기본값 = 워커별 워크트리 격리.** 공유 메인 트리에서 여러 워커가 작업하던 방식은 폐기(브랜치 혼선·컨펌 굶김 실사고). 병렬성은 "여러 워커가 한 브랜치"가 아니라 "워커별 독립 브랜치"에서 나온다.

- **메인 트리(`/{repo}`)는 `main`에 고정, stable home.** 워커 코드 작업 금지. 팀장이 여기서 git 교차검증(읽기)만.
- **각 PR/워커 = 자기 워크트리** `.claude/worktrees/wt-{ticket}` + 자기 브랜치(`fix|feat/PROJ-xxx`), **origin/main 기준 분기.**
- 커밋은 feature 브랜치 → push → **PR → main 머지**(main은 ruleset 보호). "approve = main 커밋"이 아니라 "approve = feature 브랜치 커밋".

> ⚠️ **워크트리 생성 직후 셋업 필수** — gitignored 파일(env·`.claude/team`)이 딸려오지 않는다.
> 절차: **`reference/worktree-setup.md`**. 팀장은 배분 브리프에 "wt-{ticket} 생성 + 그 체크리스트"를 명시.

## 컨펌 신호 프로토콜 (요약 — 상세는 `reference/confirm-protocol.md`)

커밋 전 컨펌을 사람이 탭을 오가며 전달하지 않고, **파일 신호 + 백그라운드 감시**로 팀장 세션에 모은다.

**신호 디렉토리**: `{프로젝트}/.claude/team/confirm/`
- `{인스턴스}.request.md` — **팀원 작성**. 유형(`CONFIRM`/`BLOCKED`/`DISCUSS`) + 한일 요약 + 간략 테스트 플랜 + 변경 파일.
- `{인스턴스}.reply.md` — **팀장 작성**. 첫 줄 `APPROVE` 또는 `FIX`. APPROVE면 `---` 뒤에 `NEXT:` 브리프를 실을 수 있다(🔴 그때는 `briefs/`에도 반드시 write).
- 사이클 종료 시 **팀원이 두 파일 모두 삭제**. 잔여 파일 = 미처리 신호.

**팀장 감시 명령** (배분 완료 후 `run_in_background: true`):
```bash
# ⚠️ zsh는 매칭 없는 글롭이 fatal — find 기반 필수
# ⚠️ 감지 결과를 변수로 받아 바깥에서 판단 — while 안의 exit는 서브셸만 죽인다
for i in $(seq 1 240); do f=$(find .claude/team/confirm -name "*.request.md" 2>/dev/null | while read -r x; do [ ! -f "${x%.request.md}.reply.md" ] && echo "$x"; done | head -1); if [ -n "$f" ]; then echo "$f"; exit 0; fi; sleep 15; done; exit 1
```

- request 감지 → **git diff 교차검증** → 사용자에게 한일 요약+테스트 플랜 제시 → 판단 → reply 작성 → 감시 재시작.
- 🔴 감시 루프는 **보조 수단**이다 — 팀장은 매 턴 시작 시 `confirm/`을 직접 확인한다(「이것만은」 10번). 루프가 살아 있는지 확신할 수 없으면 확인부터.
- `BLOCKED`는 의사결정 요청, `DISCUSS`는 기술 논의 요청(git diff가 아니라 **근거 대 근거 판단**).
- 타임아웃 시 **백오프**(1h→2h→4h).

> 커밋 게이트 훅·훅 인스턴스 미구분 버그·코파일럿 폴링 특칙·워커 측 폴링 명령: **`reference/confirm-protocol.md`**

## 검증·체크포인트

- 팀장은 보고를 **git으로 교차검증**(`git show --stat`, grep) 후 TASKS 갱신.
- **검증 1차는 워커 자기-스모크다** (2026-08-19). 팀장 1차가 아닌 이유: 팀장은 코드를 못 고쳐서 어차피 워커로 되돌아가고 그 왕복이 유휴를 만든다. 워커가 [돌려보기 → 고치기 → 재확인]을 컨펌 요청 **전에** 끝내고 증거를 첨부한다(브리프 규격 「스모크 시나리오 블록」). 도구 확장(Playwright MCP·야간 무인 루프)은 REGISTRY 검토 후보 참조 — 단계적으로.
- 체크포인트 검증(테스트 전체/빌드/E2E)은 팀원에게 명령, 팀장은 결과 확인.
- 런타임 검증(LLM 실연, 외부 서비스 연동)은 자동 검증 한계를 명시하고 **사용자 직접 확인 항목**으로 분리.
- 📌 **유닛테스트·CI가 전부 green이어도 실 LLM·실환경을 돌려야만 나오는 결함이 있다.** LLM 워크플로우·외부 연동이 걸린 변경은 **실행 검증을 별도 태스크로 배분**한다(PROJ-1028 실사고: 테스트 1900건 통과했는데 DB CHECK 제약이 v3 verdict를 막아 셀프체크가 통째로 실패).

**스모크 핸드오프 표준 4종 세트** (2026-07-14 → 2026-08-11 확장): 사용자가 "스모크하겠다"/"시나리오 줘"라고 하면 팀장이 **항상 아래를 한 번에** 제공한다.

1. **시나리오에 맞게 서버 기동** — 검증 대상 코드가 있는 트리에서. **커밋 전 변경이면 그 워크트리**, 머지 후면 메인 트리.
   셋업: 인프라 컨테이너 확인(`docker compose up -d postgres redis`) → 대상 트리 `env.local` **전 앱분** 없으면 복사 → 포트 잡은 stale 서버 종료 → **전 앱 기동**을 `run_in_background: true`로 → 리스닝 + 로그 확인 → **기동 시각 명시**(dev api는 HMR 없어 커밋 자동반영 X).
   - ⚠️ **런타임이 쪼개지면 기동 목록도 늘어난다**({app-repo} 2026-08-18 기준 **5종**: postgres+redis · llm 6060 · api 8080 · **socket 7070** · web 3000). 앱 하나를 빠뜨리면 스모크가 통째로 무효인데 **에러가 안 나서 못 알아챈다** — api만 띄우면 LLM이, socket을 빠뜨리면 실시간 진행률이 조용히 죽는다. **앱이 분리되는 PR이 머지되면 그날 `_local-runtime.md`를 갱신해라**(socket은 PROJ-940 분리 후 2주간 문서에 없었다). 프로젝트별 절차는 그 파일이 SSOT.
   - 🔴 **기동 전 '지금 그 포트를 잡은 게 어느 워크트리인가'를 먼저 확인해라** (2026-08-18 실사고 — 3000·8080·6060을 머지돼 죽은 `wt-894`가 잡고 있었다. 08-14에도 같은 사고). `lsof -a -p {pid} -d cwd`로 트리를 확인하고, 남의 것이면 **포트가 아니라 워크트리 경로로 찾아** 그것만 kill한다. 옛 코드를 보고 '버그다'로 오판하는 게 이 사고의 결과다.
   - ⚠️ Redis 등 공유 백킹서비스는 **워크트리별 키 네임스페이스 분리**(`REDIS_PREFIX=local:{ticket}`). 다른 워크트리의 stale 프로세스는 포트가 아니라 **워크트리 경로로 찾아 kill**해야 한다.
2. **로그 tail 명령 동봉** — 백/프론트 백그라운드 output 파일 경로.
3. **체크 시나리오** — 사용자가 브라우저에서 밟을 항목과, **팀장이 DB/git으로 확인할 항목**을 구분해 제시. **2026-08-19부터 브리프의 `[기계]` 항목은 워커가 이미 돌려 증거를 첨부한 상태여야 한다** — 사용자에게는 `[사용자]` 항목 + 워커 증거 요약만 넘긴다. 워커 증거가 없으면 스모크 핸드오프 전에 워커에게 먼저 돌려보내라.
4. **⭐ 바로 쓸 수 있는 기존 데이터** (2026-08-11, 사용자 요청) — 시나리오를 밟을 **실제 프로젝트·케이스를 DB에서 찾아** 프로젝트명 + URL(또는 project_id) + 시나리오에 맞는 근거까지 함께. **사용자가 매번 새 프로젝트를 만들게 하지 마라** — 스모크에서 가장 반복되는 낭비다. 없으면 "없음 + 신규 생성 필요" 명시.

## 세션 수명주기

**워커 (탭 모드)**
- **세션 시작**: 워커 탭에서 `/pairi` / `/metamong` — 정체성 로드 + 기력회복(자기 보고 파일 → TASKS/PROGRESS → git 교차확인) 후 브리프 대기.
- **세션 유지가 기본**: 태스크마다 clear하지 않는다. 같은 도메인 연속 태스크는 쌓인 컨텍스트가 자산.
- **리셋 기준** — 아래 중 하나면 리셋 후 기력회복: ①**도메인 전환**(BE↔FE 등, 오염 방지) ②**컨텍스트 압박**(잔량 ~20% 이하 또는 품질 저하 체감 — 대형 태스크 **시작 전에** 선제 리셋) ③**대형(M+) 태스크 착수 직전**.
- **연속성 원칙**: 세션은 소모품, 상태는 파일에 — 정체성(`agents/{name}.md`), 이력(`reports/{name}.md`), 프로젝트(TASKS/PROGRESS), 코드(git log). **보고 파일 기록 생략 금지.**
- 세션 사망은 예외가 아니라 상시 리스크다(장시간 작업·네트워크 오류·리밋). 복구 키워드는 **"이어서"** — 워커가 ①브리프 파일 ②reply 파일 순으로 읽고 재개.
- **복구 브리프 작성법**: ①맨 위에 "이전 태스크는 끝났다" 명시 ②팀장이 git으로 확인한 **진행도 표** ③"이 표는 밖에서 본 것이니 `git diff`로 직접 확인하고 시작하라" ④끊기기 직전의 좋은 접근이 있으면 **명시적으로 살려준다**(맥락이 날아갔으므로).

**팀장 세션 (2026-08-13 신설)**
- **기본은 compact로 이어간다.** 팀장은 워커와의 라이브 연결(cross-session 주소·백그라운드 감시 루프)을 들고 있어 새 탭 비용이 워커보다 크다 — 새 탭이면 `ListAgents` 재탐색 + 감시 재무장이 필요하고, 재무장을 잊으면 컨펌 요청을 놓친다.
- 🔴 **단, compact 직전에 `/save-progress`를 먼저 돌린다.** compact도 요약 과정에서 잃는다(2026-08-13 실측: `ways-of-working.md`가 "too large to include"로 잘림). 상태가 파일에 내려가 있으면 compact든 새 탭이든 안전하고, 안 내려가 있으면 **둘 다 위험하다.**
- **새 탭이 나은 시점**: ①**국면 전환**(PR 리뷰 큐 투입 완료 → 다음 스토리 착수 등 — 워커도 유휴라 연결 손실 비용이 0) ②하루 시작 ③사용자가 판단 품질 저하를 느낄 때(이 감각이 가장 정확하다).
- **`/compact`는 남길 것을 지시해서 돌린다 (2026-08-27 신설)**: 자동 컴팩션은 무엇이 중요한지 추측한다. 팀장 표준 지시문 — `/compact 현재 배분 상태(워커별 브리프·컨펌 대기)·오늘 내린 결정과 이유·미해결 FIX·다음 배분 후보만 남겨. 조사 과정과 중간 시도는 버려도 됨`. 시점은 **작업 사이 휴지기**(컨펌 사이클 사이) — 작업 중간 자동 컴팩션은 맥락을 잃는다. 컴팩션 뒤에는 supporting 파일(ways-of-working 등)이 **대화에서 사라진 상태**이니 필요 절만 다시 읽는다(전체 재독 금지 — 세션 시작 비용을 두 번 내는 셈).
- **모델·effort는 세션 시작 때 정하고 중간에 바꾸지 않는다** (2026-08-27 — 강의 S1 검증: `/model`·`/effort` 변경은 프롬프트 캐시 접두사를 깨 다음 턴 전체를 재계산한다. `/rewind`·Skill 호출·서브에이전트 스폰은 캐시를 지킨다). 워커도 같다 — 브리프의 모델 지정은 **세션 기동 전**에만 유효하고, 돌고 있는 워커에게 모델 변경을 지시하지 않는다.
- **불변 규칙은 `memory/`에 둔다.** memory는 매 세션·매 compaction마다 재주입되지만 스킬 supporting 파일은 아니다 — 잊으면 사고 나는 규칙이 이 파일에만 있으면 compaction 때 날아간다.

### 워커 트리 규칙 추가 (2026-08-25 — 파이리 41차 근접 사고)

- **다른 워크트리에서 만든 파일을 `cp`로 가져오지 않는다.** 트리마다 base가 달라 같은 경로의 파일 내용이 다르다. 파이리가 `wt-1067`의 파일을 `wt-restore`에 `cp`해 **의도치 않은 107줄 삭제**가 났고, `git show --stat`의 삭제 수가 기대(추가만)와 안 맞는 걸로 잡았다. 옮길 것은 `git cherry-pick`/`git show <sha>:<path>`로, 수정은 **그 트리 파일 위에 직접**.
- 같은 종류: 메타몽 *"되돌리기는 커밋 후에만"*(`git checkout HEAD -- f`가 커밋 전엔 base로 감). 둘 다 **기준 트리/기준 커밋 오인**이다. 커밋 전 `--stat`의 +/− 수를 **기대값과 대조**하는 습관을 워커 체크리스트에 둔다.
- **main을 병합/rebase한 워크트리는 `pnpm install`부터.** 새 `workspace:*` 의존이 들어오면 `node_modules` 심링크가 없어 **무관한 앱의 typecheck가 깨지고 pre-push가 막힌다**(2026-08-25 파이리 44차: #294가 `apps/llm`에 `@{app-dir}/utils` 추가 → push 3회 차단, TS6305 25건은 전부 그 파생 노이즈). 브리프의 "main 반영" 단계에는 항상 `pnpm install --frozen-lockfile`을 붙인다.
- **DEV Playwright**: `https://dev.example.com`는 **`/dev` 접두 경로**로 서비스되고 `access_token` 쿠키 path가 `/dev`라 루트 경로 호출은 401. `role-login`(`/dev/api/auth/testing/role-login`, `{test-user}`)으로 로그인 후 페이지·API 전부 `/dev/...`. 공용 환경이므로 **쓰기 동작 금지**(2026-08-26 파이리 50차).
- **스크립트로 파일 편집 시 `assert` 필수** — `str.replace`가 들여쓰기 차이로 no-op이면 "수정 완료" 로그만 남고 원본 그대로다(파이리 50차, 2회 무시됨). 팀장의 python 편집도 동일하게 `assert old in s`.
