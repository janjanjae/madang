# 설명 게이트 (상세)

> 2026-10-23 신설. **로컬 스모크를 통과하고 최초 PR(Draft)을 발행하기 직전**에 읽는다.
> 목적: 사용자가 **자기 이름으로 올라가는 코드를 자기 말로 설명할 수 있게** 하는 것. 코드 품질 심사도, 정답 시험도 아니다.
> 배경: 워크플로우가 "빨리 만들고 올리기"에 최적화돼 있어 사용자가 PR 주인인데도 "이건 왜 이렇게 했어요?"에 답하지 못하는 일이 생겼다. 별도 탭으로 띄우는 해설 팀원(조잘)은 바쁠 때 아무도 부르지 않았다. 그래서 **어차피 지나가는 자리(PR 직전)**에 짧게 끼운다.

## 켜짐 여부 — `tracker-config.md`가 정한다

프로젝트의 `.claude/team/tracker-config.md` 「타입」 절에서 판정한다.

| `설명 게이트` 항목 | 결과 |
|---|---|
| `on` / `off` 명시 | 그대로 따른다 |
| 항목 없음 + 타입 `jira` | **on** (팀 프로젝트 = 동료에게 설명할 일이 생기는 곳) |
| 항목 없음 + 그 외 타입 / 파일 없음 | off |

## 언제

- 「이것만은」 6-B의 **① 로컬 스모크(사용자) 통과 → ② Draft PR 사이**에서 **PR당 1회**만 한다.
- **하지 않는 때**: 컨펌(APPROVE)마다 하지 않는다(너무 잦다). 이미 발행된 PR의 리뷰 반영분 push에도 하지 않는다. 문서·테스트만 바뀐 PR에서도 하지 않는다.

## 어떻게 (5분 이내)

1. 팀장이 PR 범위의 diff(`git diff $(git merge-base origin/main HEAD)..HEAD`)를 보고, **이 PR에서 리뷰어가 물을 법한 지점**을 골라 질문 **2개**를 한 번에 낸다.
   - ① **구조**: "○○을 왜 A가 아니라 B에 뒀나요?" / "왜 이 방식이고 다른 방식은 아니었나요?"
   - ② **영향**: "□□가 바뀌거나 실패하면 어디가 영향받나요?"
   - 질문에 `파일:라인`을 붙여 사용자가 바로 열어볼 수 있게 한다. 용어 시험("클로저가 뭐죠?") 금지 — **이 diff에 대한** 질문만 한다.
2. 사용자는 **한두 줄로 답한다.** "모르겠어"도 유효한 답이다.
3. 팀장 피드백은 **3줄 이내**로 한다. 맞은 부분 → 틀리거나 빠진 부분 → (모르겠다고 했다면) 설명. 설명했다면 사용자가 **자기 말로 한 줄** 다시 쓰면 통과다.
4. 통과한 답을 다듬어 PR 본문 `## 변경 설명`에 넣는다(아래).

## PR 본문 기록

```markdown
## 변경 설명
- **구조**: {사용자 답을 다듬은 1~2문장 — 1인칭 작성자 설명}
- **영향 범위**: {사용자 답을 다듬은 1~2문장}
```

- 「이것만은」 7의 금지어 규칙을 그대로 지킨다. Q&A 형식, 팀장·워커 이름, `.claude/**` 경로를 넣지 않는다. 리뷰어에게는 **작성자가 쓴 설계 메모**로 보여야 한다.
- 다듬는 범위: 문장만 고친다. 사용자가 말하지 않은 근거를 팀장이 지어 넣지 않는다. 그러면 다시 "설명 못 하는 PR"이 된다.

## 패스

- 사용자가 "패스"라고 하면 바로 넘어간다. PR 본문에는 아무것도 넣지 않는다(회사 PR에 내부 운영 흔적을 남기지 않는다).
- 팀장은 `.claude/PROGRESS.md` 해당 세션 블록에 `설명 게이트 패스: PR #{번호}` 한 줄을 남긴다.
- **3회 연속 패스**면 다음 게이트에서 한 번만 "최근 3번 패스했어요, 이번엔 하나만 해볼까요?"라고 묻는다. 조르지 않는다.

## 조잘에게 넘기기 (선택)

사용자가 "조잘한테 넘겨"라고 하면, 팀장은 Q&A(질문·사용자 답·팀장 피드백·`파일:라인`)를 `.claude/team/edu/inbox-{날짜}-{주제}.md`에 쓰고 끝낸다. 조잘이 기동돼 있으면 감시로 집어 가고, 아니면 다음 `/narrator` 기동 때 처리한다. **게이트 통과는 이걸 기다리지 않는다.**
