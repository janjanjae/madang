# 사고 경위·근거·실측 (ways-of-working 부록)

> `ways-of-working.md`에서 2026-08-31 분리. 본문은 규칙만, 여기는 **왜 그 규칙이 생겼는지** — 사고 경위·실측 수치·폐기된 이전 규칙. 규칙 번호/절 이름으로 찾는다. 새 사고가 나면 **본문에 규칙 1~2줄 + 여기에 경위**를 같이 적는다.

## 「이것만은」

- **1 · Write 한 번** — 워커 폴링은 첫 md5 변경 즉시 깨어나 뒤에 Edit으로 덧붙인 항목을 못 본다.
- **2 · briefs 먼저, reply 나중 (2026-08-25)** — 워커는 reply를 읽고 그 시점의 브리프 md5를 기준선으로 잡아 폴링을 시작한다. 같은 시각에 쓰면 이미 새 내용이 기준선이라 변경이 영원히 감지되지 않는다. 메타몽이 19분간 대기했고 팀장이 "유휴"로 오인했다. NEXT를 reply에만 실으면 세션 사망 시 브리프가 통째로 소실되고 워커는 끝난 일을 다시 하려 든다.
- **3 · 감시 명령 (2026-08-26, 같은 날 2건)** — ① `for f in "$C"/*.request.md`: 매칭 0건이면 zsh fatal이라 `confirm/`이 비는 순간 감시가 즉사. ② `for f in $(find ...)`: zsh는 unquoted 확장을 단어분리하지 않아 request가 2개가 되는 순간 개행 붙은 한 덩어리가 되어 `-e`에서 조용히 탈락 — **파이리 컨펌 45분 방치.** `while ... done < <(find ...)` 안의 `exit 0`은 서브셸만 죽여 감지하고도 타임아웃. 유휴 판정 조건("보고가 브리프보다 새로운가")이 없으면 기동 전까지 45분마다 워커 수만큼 반복 발화(08-27 해소).
- **6-B · Draft 게이트 (2026-08-24 사용자 확정)** — 로컬·Preview 두 스모크를 다 거치면서도 미검증 PR을 리뷰어에게 노출하지 않는 장치. 리뷰 반영분에 Preview를 쓰는 이유: 환경 충실도·준비 비용이 로컬보다 유리(특히 blob은 워크트리 로컬이라 케이스 준비가 자주 어긋난다). **같은 날 팀장이 판정을 건너뛰고 949(PR #292)를 로컬 스모크 없이 발행시켰다** — 자기가 쓴 규칙을 몇 시간 뒤 어긴 것. 사용자 지적으로 Draft 전환.
- **6-C · 중간 저장 (2026-08-24)** — 파이리 세션이 API 529로 멈췄을 때 3시간 30분치 조사가 세션 안에만 있었다(reports 10:47 정지). 「2」와 같은 원리를 워커 산출물에 적용.
- **9 · 마이그레이션 타임스탬프** — 2026-08-14 PR #260 `DB Migration Guard` fail. rebase가 원인: 브랜치 작성 시점엔 맞았어도 main에 더 늦은 마이그레이션이 들어오면 역전. 2026-08-20: `origin/main..HEAD`는 양방향 diff라 main에만 있는 파일까지 잡혀 0건 추가 브랜치가 1건으로 나옴 → merge-base로 정정. 2026-08-18(DEV 배포 4일 중단): Guard의 `BASE_SHA`는 `github.event.pull_request.base.sha`(PR 마지막 push 시점의 main tip)라 그 뒤 main에 들어온 마이그레이션은 재검사되지 않는다. `DUPLICATE_TIMESTAMP` 검사는 07-13부터 있었는데도 통과 — 검사 항목이 아니라 **실행 시점**이 문제. 레포 설정 `strict_required_status_checks_policy: False`라 낡은 브랜치가 그대로 머지된다. 파일명을 바꾸면 `pgmigrations`의 구 이름과 어긋나 이미 적용된 환경에서 재실행된다.
- **10 · 매 턴 confirm 확인 (2026-08-19)** — 파이리 컨펌 요청 09:13 → 팀장 발견 11:30, **2시간 17분 유휴.** 루프는 세션 교체·컨텍스트 압축·다른 작업 몰입으로 끊기지만 턴 시작 시 `ls confirm/`은 안 끊긴다.
- **11 · typecheck까지 리허설 (2026-08-19)** — cherry-pick "충돌 0, 거의 공짜"라고 보고했는데, git이 자동 병합한 파일에서 한쪽이 좁힌 타입과 다른 쪽의 문자열 비교가 의미 레벨에서 죽어 정렬이 사라졌다(PROJ-1064 정렬 × PROJ-1086 라벨). 예외도 테스트 실패도 없었고 상대 브랜치의 테스트가 우연히 잡았다.
- **12 · request 재독 (2026-08-20)** — 꼬부기가 13:49 인벤토리를 올린 뒤 14:05 같은 파일에 PROJ-1116 구현 완료·컨펌 요청을 추가. 팀장이 13:49 시점 내용으로 14:37에 답해 1116 컨펌이 통째로 누락, 워커는 컨펌을 기다리며 유휴.
- **13 · 조건식을 열어라 (2026-08-26)** — 꼬부기가 갈래 09 라벨을 「미통과 항목 소명하기」로 제안하고 팀장이 그대로 올렸는데 `hasFail = failPending + unverified > 0`이라 소명·보완 두 길이 다 열린 상태. 한쪽만 부르는 라벨은 고치려던 문제의 거울상. 사용자가 *"보완할 건 없고 소명만 있는 상태인거야?"*로 잡았다. 꼬부기 설계 안에도 모순("가르지 않는다"로 확정하고 라벨은 한쪽만). **외삽 금지 (2026-08-27, 하루에 4번, 전부 사용자가 잡음)**: 코드에 컴포넌트가 있다→화면에 있다(`WorkflowSelector`는 import 0건) / 디스크에 파일이 없다→파일트리가 빈다(실제 화면 정상) / main 테스트가 깨진다→모든 PR CI가 붉다(`nx affected` — web 미변경 PR은 `Test web`이 안 돈다) / 티켓이 "Preview에서 확인"→Preview에서 확인된다(PR마다 스키마 분리, 과거 데이터 없음). 같은 종류: 08-25 `sourceFileId` 실물을 안 보고 승인, 08-19 cherry-pick 텍스트 레벨 종료.
- **14 · 절대경로 (2026-08-26)** — 상대경로 heredoc이 조용히 실패해 브리프가 아예 안 만들어졌는데 성공한 줄 알고 넘어갔다.
- **15 · 회의 결론 대조 (2026-08-27)** — tracker 수정을 별도 PR로 내라고 지시했는데 전날 시연 회의가 정반대로 결론("자잘한 PR이 계속 올라와 리뷰 부담 → 관련 수정은 묶어서 PR"). 회의록을 읽고 백로그 정리까지 해놓고 하루 만에 어김. 같은 날 지시를 세 번 뒤집었다(워커 커밋이 작아 버려진 건 없었지만 팀장이 안전하게 지시한 결과가 아니다). "팀 전체가 막혀 있다"는 근거가 `nx affected`로 반증됐는데 결론(별도 PR)만 남겨뒀다 — 근거 철회 시 결론을 재검토하는 절차가 없었다.
- **16 · pre-push 충돌 (2026-08-27, 같은 날 두 번)** — PROJ-1039 브리프가 "tracker 2건 실패는 정상(main 병합으로 해소)"이라 해놓고 동시에 "네가 main을 병합하지 마라"라고 못박아 우회로가 없었다. 워커는 `--no-verify`를 임의로 쓰지 않고 사용자 승인을 받아 처리 — 규율대로였지만 왕복이 늘었다.

## 운영 모델

- **로컬 스모크 필수 (2026-08-18 사용자 확정)** — 팀장이 스모크 순번을 이유로 PR을 먼저 올리자고 제안한 것이 계기.
- **Jira 관할 = 내 assignee (2026-08-20)** — 보안점검 지적 4건(긴급 2건 포함)이 담당자 null이었는데 팀장이 우리 백로그로 읽고 *"오픈일인데 PRD 인증 우회가 뚫려 있다"*며 워커 재배치를 제안 — 다른 팀원이 이미 처리 중이었다.
- **duedate = PR 묶음 (2026-08-20)** — 사용자 질문 *"1085는 일정에서 빠져 있는데 언제 하나"* — 코드는 이미 커밋돼 999 PR에 실려 있었는데 배분 시점에 Jira를 안 갱신해 현황판에서 사라져 있었다. 생성 시점에 비우는 이유: 스모크 중 개선 건이 쏟아지는데 그때마다 기한을 고민하면 스모크가 끊기고 그 순간엔 크기·우선순위·담당 정보가 없다. 하루 PR 1~2개라 날짜가 사실상 묶음 식별자. 같은 날 PR이 2개면 날짜로 구분 안 되지만 라벨로 더 인코딩하는 건 관리비용 > 이득. 구 "Jira는 PR 후에만" 규칙은 폐기.
